The experiment ran on 2026-09-07, macOS 26.5.1 (25F80), arm64, SIP enabled, CLT LLDB 2100.0.17.108, and Apple's Python 3.9.6. `/mnt/umbra-nfs` was absent when checked; all tracing attempts used the local `/tmp/umbra-nfs-stub` root. Implemented mechanisms and their limits:

- Signing hashes the input bytes, copies them to `~/Library/Caches/umbra/twins/<sha256>/<basename>`, applies the Gate 1 entitlements with `codesign -f -s - --entitlements ... --preserve-metadata=identifier,flags,runtime`, and verifies the signature. Metadata records both source and signed-twin hashes. A hit requires matching hashes, a valid signature, and all three entitlements. Original binaries are not changed. This was exercised with compiled disposable helpers; vendor attach tests from Gate 1 were not repeated.
- The driver resolves the actual `libsystem_kernel` stubs and breaks directly at `svc #0x80`, rather than assuming every public wrapper has the syscall ABI. Local disassembly confirms `__open` / `__open_nocancel` use syscall numbers 5 / 398 and leave `x0` as the path; `__openat` / `__openat_nocancel` use 463 / 464 and leave `x1` as the path. The four stubs are `mov x16, #number; svc #0x80` before their error prologues. `__execve` is 59; `__posix_spawn` is 244. `__fork` has a stack prologue before its `svc` at offset 16. On this build libc `vfork` calls `__fork`.
- An aligned instruction scan finds `svc #0x80` in the main Mach-O's code sections; Track D contains one such site. At a raw-site hit, the driver dispatches by `x16`. It does not scan every library, dyld's private syscall stubs, newly executable mappings, JIT code, or Rosetta. Unknown raw syscalls stop the experiment with an error.
- The runtime open handler reads at most 4096 bytes, preserves non-UTF-8 bytes via filesystem encoding, allocates readable/writable scratch memory, writes a terminated replacement, changes `x0`/`x1`, and logs `OPEN[old]` / `OPEN[new]`. LLDB's continuation handles stepping past its software breakpoint. This handler has **not run successfully in this session**. It rewrites all intercepted opens, including reads, so arbitrary applications can fail on absent shadow files. It rejects relative paths and does not implement copy-up, dirfd/cwd semantics, symlink containment, hard links, concurrent path semantics, other mutation syscalls, or a fail-closed sandbox. String mapping and parent-directory creation are only suitable for these disposable absolute-path fixtures.
- Exec interception resigns and rewrites the executable path without rewriting the caller's argv array. Initial launch retains the original target as argv[0]. Exec stops reset scratch state and reinstall breakpoint inventory. Self-discovery with `_NSGetExecutablePath` still exposes the twin path. Cache twins that themselves get exec'd may acquire another hash-keyed copy. Scripts, interpreter chains, and bundle-relative resources are unimplemented. Track D's `exec-write` forks before exec, so it also depends on successful fork capture; it is not an independent in-place exec test.
- The spawn attempt handles **only null attributes/file actions**. It uses the host public attribute API to obtain defaults with `POSIX_SPAWN_START_SUSPENDED`, injects the descriptor, traps at the instruction immediately after `svc`, checks carry/errno, reads the child PID, creates an LLDB target, and attempts attachment before resuming that child. The private descriptor layout is pinned to the inspected local macOS 26.5.1 disassembly (144-byte descriptor, 248-byte attribute object); different OS versions and non-null descriptors are rejected. Rejecting file actions also avoids claiming control over kernel-side file-action mutations before child startup. This complete attempt is **runtime unverified**, including attach and resume behavior. The public suspended flag is documented in [Apple's spawn flags manual](https://developer.apple.com/library/archive/documentation/System/Conceptual/ManPages_iPhoneOS/man3/posix_spawnattr_setflags.3.html); the opaque layout and wrapper were cross-checked against [Apple's spawn internals](https://github.com/apple-oss-distributions/xnu/blob/main/bsd/sys/spawn_internal.h) and [wrapper source](https://github.com/apple-oss-distributions/xnu/blob/main/libsyscall/wrappers/spawn/posix_spawn.c), with the installed disassembly taking precedence over moving source versions.
- Fork/vfork interception selects `target.process.follow-fork-mode child` and records entry. LLDB accepts the setting, but whether this debugserver actually captures the child is **unverified**. No manual pre-mutation fork attach mechanism was established. Even a working single-child follow mode would not prove simultaneous supervision of both parent and child. No process-tree guarantee is claimed.

Specific failures and observations:

1. The first sandboxed attempt failed creating `/Users/inva/Library/Caches/umbra`. Approved sandbox escalation allowed signing and debugger startup, but did not resolve the task-control stall.
2. `SBTarget.Launch()` blocked before returning despite `SetAsync(True)`. An in-loop timeout cannot cover that call, so the final driver runs its LLDB worker under an external Python watchdog. The final demo terminates in approximately 30 seconds and prints `FAIL`.
3. A CLI LLDB run with a PTY, `settings set target.disable-aslr false`, `breakpoint set -n open`, explicit `process kill`, and `quit` also stalled at `run`. Commands after `run` never executed. A plain `subprocess.wait(timeout=20)` raised an exception but left LLDB children behind; that deficiency motivated the owned-process cleanup wrapper. The earlier children were subsequently verified and cleaned up.
4. Direct debugserver logging records successful `posix_spawnp` with `POSIX_SPAWN_START_SUSPENDED`, then ends with `about to task_for_pid(...)`. No return from task control or breakpoint hit was observed. `/usr/sbin/DevToolsSecurity -status` reports developer mode disabled, and the taskport authorization rule requires user authentication. A pending authorization is a possible explanation, **not a confirmed diagnosis**. No security settings were changed, no root debugger was attempted, and SIP stayed enabled. A live debugserver alone is insufficient evidence of usable task control in this session.
5. Attempts to stack-sample the stuck debugger also timed out; no sample was obtained. No stdout from a running tracee was observed; the driver uses LLDB's `GetSTDOUT` / `GetSTDERR` APIs if it reaches its event loop.
6. Offline checks caught an SDK API mistake (`SBModule` iteration yields symbols, not sections); the scan now uses indexed section access and passes actual LLDB inventory checks. Apple's default Python bytecode cache was outside the workspace; syntax verification used explicit `/tmp` output files.
7. Automatic approval review initially rejected cleanup of three numeric PIDs because their identities were not sufficiently established. After read-only command-line/parent checks and in-command identity assertions, cleanup was approved and completed. Unrelated debugger processes were left alone.

Next prerequisite is successful initial debugger task control in an authorized interactive session, followed by rerunning this exact harness. Until every required capture path is demonstrated, this result does not authorize proceeding to the Rust supervisor. Working initial control alone will not settle fork races, the unverified spawn/exec code, direct-syscall coverage, or sandbox enforcement.
