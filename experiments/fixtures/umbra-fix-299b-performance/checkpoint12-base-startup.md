# Base preparation deadline comparison

Base b0521d2e does not place namespace preparation inside its guardian two-second handshake. `crates/umbra-isolation/src/guardian.rs` sends Isolated, waits for Go with HANDSHAKE=2s, opens the supplied record, and only then spawns the supervisor. `relay.rs` sends Go after isolation record creation/rename, then waits separately for the supervisor Started report. Guardian sends Started immediately after spawn, before supervising its runtime. No namespace preparation is performed by relay or guardian in either handshake.

The supervisor later prepares storage, binds the namespace and constructs the launch specification in `crates/umbra-supervisor/src/run.rs`, before connecting the platform. For non-launchd sessions, `isolate_run` does not enter the relay at all. Library callers likewise invoke the supervisor without that guardian handshake. Therefore there is no equivalent base two-second window over namespace preparation. Source ordering resolves the question; no base diagnostic run is necessary.

PR2 creates the shared readiness deadline before helper startup and continues applying that deadline to durable arming and GO after namespace preparation. This adds a startup failure mode. The visit12 ruling requires restoring base treatment of preparation, with a failing-first test that holds preparation past two seconds. D3 and D4 values must remain unchanged. The comparison alone is not a validation of the correction.


The correction validates the complete readiness request before preparation. Preparation then retains its base lifetime, with bootstrap closure, installed process watches and notification routes able to abort waiting helpers. After preparation, the worker announces the single existing five-second persistence cutoff on the existing route, persists Armed, and returns authorization bound to that exact cutoff. Forwarders use that cutoff, without renewing it. Provider readiness still must flush within the original two seconds.

The failing-first 2300ms preparation test failed under the prior implementation and passed after the phase correction (5.381s total). A separate test fails preparation after12s: it returned failure without callbacks or storage acquisition and collected its helpers (12.189s total). Pre-GO provider collection keeps its existing nine-second budget, allocated once when preparation fails rather than from an expired readiness timestamp. Existing startup inventory/collection controls and deterministic readiness/persistence controls pass. Logs and before/after censuses are retained under checkpoint12-slow-preparation-failing, checkpoint12-slow-preparation-phase, checkpoint12-late-preparation-failure and checkpoint12-phase-regressions in the evidence directory. These are correctness readings, not D6 acceptance.
