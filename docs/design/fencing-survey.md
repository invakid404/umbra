# NFS fencing authority survey

Read-only source survey, 2026-09-09; no server inspected or disrupted. M1/M2 use cooperative handoff. M3 must qualify crash takeover on Ganesha before advertising it; DSM model/version/export qualification follows. NFSv4.0 is the first client target; 4.1 is a separate follow-up, not a hidden dependency of M1.

## What must be fenced

A successful takeover must establish a cutoff: all old mutations have either completed before that cutoff or are prevented from completing afterward; the old host cannot reconnect and submit new mutations. This includes WRITE/SETATTR and namespace operations such as RENAME/REMOVE, which do not carry an Umbra epoch. Reconcile pre-cutoff effects before releasing the new writer. A TCP disconnect, expired local timer, new epoch file or absent heartbeat alone proves none of this.

The application writer lease is distinct from the NFS client's protocol lease. External human/client edits are deliberately outside Umbra's exclusivity promise, but two Umbra instances must never be live on the same session. Do not make an application lock depend on every outside editor honoring it. See [failure model](failure-model.md).

## Ganesha: confirmed interfaces versus inferred use

Source pin for this survey: [`06528886251bbaf94f6d0aaff95cea90ef0cd748`](https://github.com/nfs-ganesha/nfs-ganesha/tree/06528886251bbaf94f6d0aaff95cea90ef0cd748), upstream `next` at inspection. This is evidence of interface behavior, not the approved deployment version; the M1 spike pins an actual build/image and records differences.

| Mechanism | What the source/protocol provides | Fencing assessment |
| --- | --- | --- |
| NFSv4.0 client/open/lock state | Client IDs, state IDs, OPEN share reservations and lease/reclaim rules. | Revoked state can reject old stateful requests. It does not attach Umbra authority to all namespace mutations or forbid establishing a new client ID. |

Per-file share-deny can also conflict with the owner's external-edit policy. Never advertise whole-session fencing from a marker lock alone. **Proposed M3 authority:** a trusted out-of-band host/network controller, separate from the potentially stalled Umbra process. Persistently isolate the old writer host from the export (or prove its termination and prevent its restart), release server state only through a separately qualified mechanism with acceptable scope, and prove all previously accepted mutations drained. Then reconcile and grant the new epoch. The surveyed Ganesha APIs do not establish a ready-made narrow per-owner fence; a dedicated endpoint or additional server integration may be necessary. Record run/old owner/new owner, fence action ID, exclusion scope, server identity, completion evidence and the acquisition order. Check that exclusion survives server/controller restart.

This is an architectural proposal requiring a dedicated qualification PR. Per-IP exclusion can affect unrelated sessions and fails to distinguish clients behind NAT; shared IPs or unidentifiable old routes are a No-Go unless the deployment supplies finer isolation. AUTH_SYS UID/GID is not a per-incarnation credential. Do not add broad firewall/host-kill permissions to an ordinary storage credential or exercise them on a user's server as part of connection setup.

Qualification must stop old A mid-call, start B, attempt old-state writes and stateless rename/unlink, reconnect A with old and new client IDs, resume A after SIGSTOP, and repeat across restart/grace. Verify server-side bytes after the cutoff, not just errors observed by B. Release and admission themselves need crash-window coverage. Ganesha-only state revocation with no reconnect exclusion is No-Go.

## Plausible DSM targets (candidates, not qualification)

DSM documents configurable maximum NFSv3/v4/v4.1 with model-dependent 4.1 support. This supports a conservative 4.0 first target. Marketing protocol lists do not establish the export's negotiated minor version, stable-storage behavior or fencing controls. [DSM NFS settings](https://kb.synology.com/en-nz/DSM/help/DSM/AdminCenter/file_winmacnfs_nfs?version=7)

| Candidate | Public evidence | Planned qualification posture |
| --- | --- | --- |
| DS220+ | [Product specification](https://global.download.synology.com/download/Document/Hardware/ProductSpec/DiskStation/20-year/DS220%2B/enu/Product_Spec_DS220%2B_enu.pdf) lists v3/v4/v4.1 and Kerberos. | Plausible older Plus-series baseline; pin installed DSM and exported filesystem before testing. |
| DS224+ | [Product page](https://www.synology.com/en-ca/products/DS224%2B) lists v3/v4/v4.1. | Plausible newer two-bay target; same protocol and persistence checks. |
| DS923+ | [Official download center](https://www.synology.com/en-global/support/download/DS923+) and DSM family documentation; model-specific English protocol PDF could not be retrieved in this survey. | Candidate only; verify exact model/DSM capability list before selecting, including 4.1 if requested. Do not infer it from neighboring models. |
| DS1522+, DS1821+ | [Synology comparison](https://www.synology.com/en-global/products/compare/DS1522%2B/DS1821%2B) lists v3/v4/v4.1 for both. | Plausible larger Plus-series targets; qualify each advertised deployment separately. |

For these candidates the public administration docs inspected expose NFS enable/version selection, host/IP export permissions, squash/security settings and asynchronous-write settings. I found no documented supported per-client-ID revoke/drain API, nor a documented equivalent of Ganesha's broader endpoint state-release hook. That is a survey limit, not proof that DSM's internal kernel has no administrative interface. SSH access, service restart or private `syno*` commands are not a supported fencing contract by assumption. [DSM permissions](https://kb.synology.com/en-global/DSM/help/DSM/AdminCenter/file_share_privilege_nfs?version=7)

Before DSM qualification pin model, DSM/build, filesystem/volume layout, export/security/squash settings, non-privileged-port allowance, cache/device configuration and effective protocol. Start with asynchronous export acknowledgement disabled; still prove stable-write behavior under storage power loss. Record whether an independent host/network fence is available. Server HA support does not imply client-writer fencing.

**Fallback:** cooperative handoff with bounded waiting. On timeout report owner unavailable and retain the marker; another host remains unable to open the live/abandoned session. Never interpret “cooperative-with-timeout” as automatic takeover after waiting. A DSM deployment may qualify remote durability while still advertising cooperative-only handoff. Safe automatic crash takeover stays a required production goal, but is unavailable on a deployment lacking a qualified fencing authority; report that capability limitation explicitly.
